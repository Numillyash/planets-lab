# Core structure construction V2: partial priority target execution

Date: 2026-10-20. Continues merged PR #248 and parked Host-external dependencies in issue #247.

## Rulebook versus implementation scope

Primary Planets.nu documentation:
- `https://help.planets.nu/planetary-structure-building` defines each structure as 1 supply + 4 MC per mine / 3 MC per factory / 10 MC per defense.
- `https://help.planets.nu/map-planet` states a target quantity for each structure; execution priority **defense -> factories -> mines**, capped by population and currently available resources, and that supplies can be sold automatically to raise MC.
- `https://help.planets.nu/supplies` documents supply sale at **1 MC per supply**.
- `https://help.planets.nu/planetary-structure-details` defines colonist caps using 200+SQRT(clans-200) mines, 100+SQRT(clans-100) factories and 50+SQRT(clans-50) defense, with lower caps equal to clans.
- `https://help.planets.nu/beginner-settings` documents the special **No Supplies** mode, explicitly unsupported here.

The existing `forecast_standard_structure_build()` v1 is left untouched. The new **separate** `forecast_priority_structure_build()` is a pure, no-side-effect model for the normal structure target sequence, not a Host event producer.

## V2 algorithm

- Require explicit standard-rule eligibility and an exact owned planet/target identity; validate numeric clans/resources/existing structures and reject downgrades or empty targets.
- Clip requested structure targets to the current clan-dependent ceiling. Existing structures can temporarily exceed the cap after a population drop; v2 does **not** silently destroy them or implement decay.
- For each target in **defense, factory, mine** order, buy as many full units as possible from the available MC+supplies. One unit consumes one supply and the documented MC price.
- With `automatic_supply_sale_enabled=True`, sell only the necessary *additional* supplies for MC, 1:1; the supply physically consumed by a purchased structure **cannot** also be sold. If a high-price structure is unaffordable, continue to the next lower-price family; no unmodeled automatic reorder.
- If the available cash/supplies do not permit every target, return a **supported conditional partial result** with per-type bought/unbuilt counts. A clipped target is also marked partial, never misreported as fulfilled.
- Cross-check the full local ledger:
  `initial_supplies - final_supplies == built_units + supplies_sold`;
  `initial_mc + supplies_sold - final_mc == sum(unit_cost * units)`.
  Negative resources, contradictory values, special modes, unknown phase order and actual server acceptance remain unsupported/unknown.

This is a deterministic **model of documented priority and exchange**, not NuHost differential parity or proof that archived net structure changes were generated by these orders.

## Regression scope

Synthetic tests check full backward-compatible V1/V2 equality for fully funded construction, 1:1 exact-cash shortage, insufficient supplies, cheap-type fallthrough, max-clan clipping, historical existing overcap after clan loss, unsupported malformed types, immutability and a 180-case budget matrix (10 MC × 9 supplies × 2 sale settings). No DuckDB or private player data is loaded.

Structure purchase placement relative to factory generation/tax and Host acceptance is not independently established; any integration must be opt-in with conditional, clearly labeled results and fail-closed incompatibilities.
