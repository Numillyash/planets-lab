## THost-reference / c2ng

Pinned source and provenance are documented in:

- `2026-09-28-c2ng-provenance-c2nu-vcr-side-mapping.md`

Key points:

```text
single pre-sorted ship vector
RIGHT outer / LEFT inner traversal
capture mutates object in place
captured ship becomes passive
fl_WasCaptured suppresses captured LEFT
no second capture-generated order
```

The one-sided captured check was deliberately added in c2ng as a reconstruction
of a claimed HOST code peculiarity.

This is useful historical candidate behavior, not Nu evidence.

## PHost 4.1h

Primary PHost documentation:

```text
https://www.phost.de/phost4doc/oob.html
```

PHost normal combat is explicitly an **Aggressor/Opponent Phase**.

Algorithmically:

1. select the next aggressor in battle order;
2. find an opponent for that aggressor in battle order;
3. perform battle;
4. if aggressor survives, seek another opponent;
5. if aggressor is killed/captured or opponents are exhausted, seek next aggressor.

PHost documentation also says that when a ship is captured:

```text
owner changes
emergency crew <= 10
ship becomes passive for further fights this turn
```

This makes an important role distinction:

```text
captured/passive ship cannot continue as an aggressor,
but passive status does not itself mean the object disappears from all
remaining opponent selection.
```

### PHost LEFT/RIGHT is not useful as a direct Nu side rule

PHost documentation explicitly states that PHost assigns the two VCR sides
randomly, so the VCR alone does not reveal aggressor/opponent.

The same paragraph explicitly contrasts HOST, where the aggressor is always on
the RIGHT.

Thus:

```text
PHost role semantics can be compared to Nu
PHost physical VCR side assignment cannot be imported into Nu
```

## Current NuHost primary documentation

Current Planets.nu Help documents:

- more aggressive combatant generally fights first and from RIGHT;
- complex stacked battle order can shift dynamically;
- each ordinary ship proceeds through its target list while alive and
  uncaptured;
- captured ships may fight for their new owners;
- captured ships can fight within the existing order;
- captured ships then receive an **additional order set anew when captured**;
- those capture-generated fights are limited.

This is structurally richer than either audited c2ng or the PHost combat page.

## Implication for the current side blocker

The active question should no longer be represented as one undifferentiated:

```text
post-capture LEFT/RIGHT rule
```

At minimum it has two documented order contexts:

```text
O = continuation inside the original ordinary order
C = additional order generated by capture
```

The same physical ship can therefore enter later VCRs under different order
contexts.

That naturally explains why simple scalar controls such as:

```text
sticky capture side
frozen priority
opponent/initiator right
fresh captured priority
```

can each fit a subset but fail globally.

This is a structural explanation only; the eight rows still determine whether
it is actually the reason for the current residuals.

## Revised discriminator

For every post-capture continuation, determine **order context before side
prediction**:

```text
1. O-only?
2. C-only?
3. reachable from both?
4. neither / reconstruction incomplete?
```

Only after that should a side predictor run.

### Candidate O behavior

Use c2ng only as an external candidate:

```text
continue original pre-sort/cursors
captured unit cannot occupy the c2ng captured-LEFT role
```

### Candidate C behavior

Do not derive C from c2ng.

Start from primary Nu documentation and observed capture-time state:

```text
new order exists
it is created at capture
general aggressor/right principle applies unless a documented/observed
stacked-order exception intervenes
```

Unknown C details remain:

- state snapshot timing;
- FC treatment;
- mission/PE treatment;
- rank within new order;
- repeated-pair/occurrence treatment;
- LEFT/RIGHT rule when role is ambiguous;
- counter/limit semantics.

## Historical PHost value

PHost provides one useful conceptual control for C diagnostics:

```text
separate logical role (aggressor/opponent) from physical VCR side
```

Nu documentation links aggression to RIGHT generally, but the analysis should
still compute these as separate fields:

```text
order context
logical initiator/aggressor
selected opponent
physical factual LEFT/RIGHT
```

This avoids baking the desired side result into opponent selection.

## Evidence classification

### Primary documented Nu

- two post-capture order contexts exist;
- new capture-generated order exists;
- aggressive combatant generally RIGHT;
- stacked order can dynamically shift.

### PHost documented reference

- explicit aggressor/opponent lifecycle;
- captured ship becomes passive;
- captured aggressor terminates its aggression sequence;
- PHost VCR side is randomized.

### THost external candidate

- c2ng directional captured-side quirk;
- original-order persistent cursor implementation.

### Still unknown for Nu

- exact C-order construction and limit counter;
- exact O-vs-C scheduling;
- exact side assignment in the residual capture cases.

## Recommended diagnostic schema

For the existing eight rows, add columns:

```text
order_context_candidate = O / C / both / unknown
logical_aggressor
logical_opponent
original_order_cursor_reachable
capture_generated_rank
factual_left
factual_right
captured_side
```

Then report side accuracy stratified by `order_context_candidate`.

This is the most bounded way to turn the external lineage comparison into a
useful official-Nu discriminator without importing external mechanics.
