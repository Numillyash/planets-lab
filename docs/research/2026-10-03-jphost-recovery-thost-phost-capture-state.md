## 1. THost nested-loop traversal: independent historical corroboration

Donovan's historical HOST documentation gives a much more explicit account of
normal ship-vs-ship order than the commonly repeated “lowest battle value fights
first” shorthand.

Source:

```text
https://www.donovansvgap.com/help/details.htm
section: Combat: order in which ships fight
```

The described algorithm is:

1. sort all ships at a location in ascending battle value;
2. take each ship in that order as the **initiator**;
3. for that initiator, check every other ship in battle-value order;
4. either unit may be the actual aggressor;
5. the **initiator**, not necessarily the aggressor, is placed on VCR RIGHT;
6. if ships survive a timeout, the reverse initiator direction can later produce
   a second fight between the same pair.

The explicit three-ship example is structurally:

```text
1 -> 2
1 -> 3
2 -> 1
2 -> 3
3 -> 1
3 -> 2
```

This is important because it independently supports the same broad traversal
shape used by the c2ng Tim-Host simulator:

```text
outer cursor   = initiator / RIGHT
inner cursor   = checked opponent / LEFT
```

This does **not** validate c2ng's captured-ship guard. It only shows that the
nested-loop cursor itself has historical HOST support independent of c2ng.

External repository:


Key historical change:

```text
76b3eed65bee4506758c258b6fc33e10d1a031ee

```

The commit introduces a runtime `fl_WasCaptured` flag and adds the asymmetric
Tim-Host test:

```cpp
if (!isPHost(type) &&
    (leftShip.getFlags() & Object::fl_WasCaptured) != 0) {
    return false;

```

Capture sets:

```text
new owner
crew = 10

```

The source comment attributes the asymmetry to reverse engineering of HOST code:
the “mission 0 and crew 10” check allegedly intended to test both ships, but a
`youship` vs `you` typo causes only the opponent/inner-side check to be
effective.

This attribution remains an **external reverse-engineering claim**. We do not
have Tim Wisseman HOST source to independently verify the claimed typo.

However, bug #428 also added explicit regression fixtures:

```text

test2.sim -> c2hosttest/combat/04_order/b
```

The Tim-Host ship fixture says its expected fight sequence is “the same as
generated by Host”. It includes a passive ship with the lowest FC battle order,
which can still be the initiator while another ship supplies aggression. That is
consistent with Donovan's independent initiator/aggressor distinction.

## 3. PHost has explicit, persistent “captured this turn” state

PHost documentation gives a useful architectural comparator, despite explicitly
warning that its combat implementation is different from HOST.

PHost 4.x AUXDATA block 101 stores:

```text
bit 0 = ship was re-crewed (captured) this turn
```

This is significant because capture is represented as an explicit intra-turn
state transition rather than inferred solely from current crew, mission, owner,
or friendly code.

The PHost fight conclusion also states:

```text
capture:
  ownership changes
  emergency crew <= 10
  ship becomes passive for further fights this turn
  damage/shield/crew/ammunition carry forward
```

And its documented Aggressor/Opponent phase is role-based:

```text
select aggressor by battle order
for that aggressor, select possible opponents by battle order
surviving aggressor continues through opponents
captured/killed/exhausted aggressor ends its aggressor pass
then choose another aggressor
```

PHost VCR physical left/right is randomized, so those physical sides are not a
THost/Nu comparator.

This yields a useful external design lesson:

```text
capture can create explicit queue-relevant state
without requiring mutation of all ordinary ship orders
```

But the PHost state machine itself must not be imported into Nu: PHost's own
documentation says combat and combat order differ from HOST and historically
used independently designed mechanics where HOST behavior was unknown.

## 4. Official Nu documentation requires more than the c2ng single cursor

Primary Nu documentation states that a captured ship can:

- continue fighting on behalf of the new owner;
- participate **within the existing order**;
- then receive an **additional order set anew when captured**;
- be limited in repeat combat, with the Host-order page stating that any two
  ships can fight each other at most twice.

This remains the strongest evidence that Nu needs at least two conceptual
post-capture contexts:

```text
O = continuation/re-entry associated with the existing order
C = additional order created at capture
```

The external investigation does not yet identify the exact C algorithm.

The 3/31 c2ng result now tells us that the THost-style frozen initiator cursor is
not a sufficient implementation of Nu's O/C behavior.

### New recovery path

SourceForge still exposes legacy CVS repositories through downloadable complete
repository snapshots. Their documented URL convention is:

```text
https://sourceforge.net/code-snapshots/cvs/<prefix>/<project>.zip
```

For project slug `jphost`, the derived snapshot URL is:

```text
https://sourceforge.net/code-snapshots/cvs/j/jp/jphost.zip
```

The current web environment cannot fetch this binary endpoint directly, so the
snapshot has **not yet been validated**.

A reproducible helper is now tracked:

```text
tools/research/fetch-jphost-cvs-snapshot.sh
```

It:

1. downloads the candidate snapshot;
2. records SHA256;
3. validates ZIP integrity;
4. locates `CVSROOT`;
5. discovers candidate modules;
6. checks out a working tree when a CVS client is available;
7. inventories files and searches Java/XML/text for combat/capture/order terms.

All recovered GPLv2 source stays under ignored `artifacts/`; it is not copied
into canonical mechanics.

This is now the highest-value unresolved source-recovery target.

## 6. Historical HOST evidence of post-capture re-use

Historical strategy material also assumes that a ship captured during the combat
sequence can remain relevant to later combat in the same turn. This is weaker
than engine documentation, but it is consistent with both modern Nu docs and the
notion of explicit post-capture state.

Do not use strategy prose as an exact queue specification; its value is only to
rule out simplistic models in which combat capture immediately removes a prize
from all further ship-vs-ship processing.
